# 04. Тестирование и проверка

Проект содержит встроенные инструменты проверки, которые включаются **только** аргументами после `--`
в командной строке (для обычного запуска ничего не меняют). Реализация — `Scripts/Dev/`.

`<EDITOR>` = `<GODOT_SRC>\bin\godot.windows.editor.double.x86_64.mono.console.exe` (консольная версия печатает вывод).
Команды — PowerShell, из корня репозитория. Перед запуском проект должен быть собран (`dotnet build sandbox-poly-game.csproj`).

## Самотесты

```powershell
<EDITOR> --headless --path . -- --selftest
```

Код выхода `0` — все тесты прошли. Последний результат в редакторе: **1043 passed, 0 failed** (экспортированная игра
после этого не пересобиралась/не перепроверялась — см. «Отдельный exe игры» в [02](02-project-setup.md)).

### Что проверяется

**Меширование и полный wireframe** (чистая логика, без сцены):
- один блок → 6 граней, 6 полигонов; два соседних блока → внутренние грани убраны, 6 полигонов;
  куб 3×3×3 → 54 грани склеены в 6 полигонов; L-образная фигура (несмотря на нерямоугольный след, полигоны склеиваются жадно);
- перекраска одной клетки разбивает полигон по цвету (10 полигонов вместо 6); блоки разных типов одного цвета склеиваются;
- блок через границу чанков (`x = 15 | 16`) и в отрицательных координатах — меширование по-прежнему корректно;
- во всех случаях выше и на случайной постройке (≈3400 блоков через границы чанков) проверяется инвариант
  **число отрезков каркаса Wireframe = число полигонов × 5** (контур + диагональ каждого полигона —
  см. [03](03-build-editor.md); у отдельного инструмента Borders — своя решётка границ клеток, без диагоналей);
- случайная постройка: видимые грани совпадают с независимым подсчётом «в лоб», склейка без потерь (сумма площадей
  полигонов = число видимых граней), у всех треугольников верный порядок вершин;
- инкрементальные обновления: после случайных правок на границах чанков каждый чанк, чей меш изменился, входит в набор «грязных».

**Рейкаст**: луч на землю (сверху и снизу), на грань блока сверху/сбоку, косой луч, ближайший блок в стопке, «в небо», земля вне области;
регрессия на 2000 случайных лучей на землю (клетка должна совпадать с аналитической; на прежней реализации ошибалась в ~40% случаев).

**Область построек** (`BuildSpace`): границы симметричны относительно центра (0,0,0) — 25 м влево/вправо и вверх/
вниз, 50 м вперёд/назад (числа считаются, а не захардкожены дважды); угловые клетки входят в область, за ними —
уже нет; `WorldMin`/`WorldMax` (мировые координаты внешних углов, используются для отрисовки границы, см.
[03](03-build-editor.md)) соответствуют этим 25/25/50 м.

**Тесты не привязаны к составу пользовательских блоков (2026-10-05, переработано 2026-10-06).** Функциональные блоки — редактируемые данные
(создаются в `--blockeditor`); с 2026-10-06 в настоящем `blocks/` их вообще нет (остались только резиновые формы, а блоки старого формата удалены),
и тесты не используют старые блоки. Поэтому: (1) проверки настоящего каталога — **инварианты каждого функционального блока, который там окажется**
(в т.ч. будущего), а не слаги и точное число блоков; (2) тесты рантайма берут блоки из **фикстурного каталога** (`BuildFixtureCatalog`: три временных XML —
куб, кнопка с поведением `Button`, мотор — пишутся в `user://selftest_blocks`, грузятся отдельным `BlockCatalog.Load` и тут же удаляются);
(3) интеграционные тесты, которым нужны именно `BlockCatalog.Instance` (спавн, призрак, `EditorState`), на время теста **подменяют каталог**:
`SelfTest.UseCatalogWith(("zz_...", "<JSON компонента FunctionalBlock>"))` собирает каталог из всех блоков настоящего `blocks/` плюс блоки-фикстуры и
ставит его через `BlockCatalog.OverrideInstanceForTesting` (по `Dispose` возвращает прежний; слаги фикстур начинаются с `zz_`, чтобы `RuntimeId`
настоящих блоков не сдвинулись); (4) модели в тестах — **самодельные `.gltf`** с известным bbox (`WriteTestGltf`: позиции и индексы в base64 прямо в
файле, пишется в `res://meshes/selftest_*.gltf` и удаляется), а не настоящие ассеты: так тесты не зависят от `meshes/` и от кэша импорта (экспорт через
движок в headless не годится — у мешей без рендерера нет вершинных данных).

**Каталог блоков** (`BlockCatalog`): загружены XML из `blocks/` (минимум 4 формы block/wedge/pyramid/inverse_pyramid); поиск по
слагу и по рантайм-id; `BaseComponent` и `BuildingBlock` (включая корректный `Shape` для каждой формы) парсятся из JSON-тела
`<Component>`. Для **каждого** функционального блока каталога: есть `FunctionalBlockComponent` и нет `BuildingBlockComponent` (не
резинится), footprint ≥ 1×1×1, масштаб положителен, слитые боксы коллизии покрывают ровно её клетки, никакие две ноды одного типа не делят клетку, физические порты только Fluid/Torque (после перехода на новый формат функциональных блоков в настоящем каталоге нет — цикл по ним пуст, пока в редакторе блоков не созданы новые). В `ResourceType`
нет `Electricity`; блока `cable` в каталоге нет. Отдельно — `EditorState` (на блоке-фикстуре 2×1×3 со смещением от корня): выбор функционального блока принудительно фиксирует
`PendingSize` в его `Footprint` (Resize не действует), и `SetSlot` на текущем выбранном слоте пересчитывает `PendingSize` сразу, не
дожидаясь следующей смены слота.

**Резиновые блоки, призрак и среда (2026-10-05)** — `RunRotatedResizableBlockTests` (клин 3×1×1 с поворотом: занятый бокс 1×1×3, `ShapeInstanceView`
рисует меш ровно в нём, `TrySetSize` на повёрнутом блоке и `MaxSize` по ЛОКАЛЬНОЙ оси) и `RunPlacementConflictTests` (интеграция через настоящий
ввод мыши): над блоком-корнем ставится 3×1×1 с соседями-препятствиями, 7 ориентаций подряд (без поворота, 4×Y, X, Z) — призрак НИКОГДА не
пропадает, красный оверлей отмечает ровно занятые/внеобластные клетки повёрнутого бокса, мировой AABB призрака == `PlaceBox`, ЛКМ по
конфликтующему призраку ничего не ставит, а в свободной ориентации ставит блок в повёрнутый бокс с его `RotationSteps`; последовательность
покрывает и конфликтную, и свободную ориентацию. Там же: `CursorPositionInViewport` (экранные → оконные координаты, курсор вне окна → null — механизм фикса
«курсор не виден при входе»), цвет фона редактора `#238baf`, ambient и солнце белые, а общий `BuildFlatSkyAndSun` по умолчанию по-прежнему берёт ambient
из неба (мир не изменился). Тест жёсткости меша: клин 3×1×1 при 6 поворотах укладывается в `RotatedSize` и является повёрнутой копией неповёрнутого.

**Поворот блока с фиксированным footprint'ом вокруг корневой клетки** (`RunFootprintRotationTests`, чистая математика — в каталоге
может не быть блока больше 1×1×1, а каталог в тесте менять нельзя): для 4 footprint'ов × 64 комбинаций ступеней — занятые клетки
`BlockFootprint.PlaceBox` = корень + повёрнутые локальные клетки; корневая клетка всегда занята; объём сохраняется, размер — перестановка
осей footprint'а; рамка поставленного экземпляра (`InstanceFrame`, по центру бокса) совпадает с рамкой призрака (`RootFrame`, по
корню); центр КАЖДОЙ локальной клетки модели/коллизии попадает в центр соответствующей занятой клетки; весь повёрнутый хитбокс
лежит внутри занятого бокса. Частные случаи: без поворота — (корень, footprint); поворот 2×1×1 вокруг собственной длинной оси
занимает те же клетки; на 90° вокруг Y становится 1×1×2 и сохраняет корень; на 180° тянется в ДРУГУЮ сторону от корня (а не
вокруг центра). Анимация призрака: при промежуточном базисе (45°) центр корневой клетки не двигается, а вторая клетка уезжает.

**Новый формат функционального блока** (чистая математика, без сцены; см. [05](05-world-and-vehicle-systems.md) «Редактор блоков»):
- *`BlockModelLayout` (`RunBlockModelLayoutTests`):* масштаб по умолчанию 0.125; bbox.min модели встаёт в (0,0,0) независимо от того, где начало
  координат модели в файле (центр и вообще вне модели); **правило якоря** на 6 наборах долей — выбранная точка bbox попадает в ту же долю клетки (0,0,0);
  смена масштаба оставляет якорь на месте; границы в рамке блока (модель 2 м = ровно клетка; якорь Max на X для модели в 2 клетки → клетки −1..0);
  **footprint из bbox**: точный 1×1×1 и 2×3×1, допуск 1% (0.5% сверх клетки — не соседняя клетка, 2% — соседняя; то же на мин. стороне), шум float
  1e-7 м не двигает и не растит footprint, отрицательный `min`, нечётный размер вокруг центра, минимум 1×1×1 (модель меньше клетки, плоская,
  плоская ровно на границе клеток).
- *`CollisionCells` (`RunCollisionCellsTests`):* параллелепипед клеток (в т.ч. с отрицательным индексом) → один бокс с точными min/size; одна клетка; пусто → нет
  боксов; несвязные группы → отдельные боксы; клетки, касающиеся только ребром, — не один бокс; L-образная фигура → 2, куб 2×2×2 без угла → 3 (минимум); на 40
  псевдослучайных наборах — покрытие ровно данными клетками, боксы не пересекаются, боксов не больше клеток, результат не зависит от порядка входа;
  `Normalize` (дубли, канонический порядок), `Expand` перекрывающихся групп, пересчёт `CellBox` в метры.
- *Разбор формата (`RunFunctionalBlockFormatTests`):* умолчания (footprint 1×1×1, якорь 0, масштаб 0.125, НЕТ коллизии); полный набор ключей;
  коллизия — дедуп+канонический порядок, L из 3 клеток → 2 бокса; ключи старого формата (`modelScale`/`modelOffset`, коллизия боксами в метрах)
  падают с понятным «legacy»; footprint < 1 и неположительный масштаб — ошибки; якорь вне 0..1 клампится; ячейка грани порта хранит отрицательные индексы.

**Параметры, провода и рантайм логики (2026-10-07; `SelfTestWiring.cs`, `SelfTestSeat.cs`, `SelfTestTools.cs`, `SelfTestRealBlocks.cs`).** Блоки для тестов — фикстуры (`UseLogicFixtures`: аккумулятор 2×1×1, мотор, вал, кнопка, сиденье со

  вращение идёт по цепочке валов, стоящих на порту мотора, и не идёт к валу с зазором; отрицательный сигнал — обратное вращение (знак сохраняется на валах); пустой аккумулятор останавливает мотор (доля питания 0); снятие провода питания
  останавливает мотор и расход; параметры у экземпляров свои (второй мотор с другими `maxRpm`/`maxPower`); два потребителя на одном аккумуляторе — заряд не уходит ниже нуля; аккумулятор: нода уровня абсолютная/долей, `initialCharge`, зарядка от

- *`RunEditorToolTests` (редактор построек, настоящая камера и экранные координаты):* **Nodes** — `N` включает, постройка полупрозрачна, вкладки слоёв на тулбаре; **слои:** по умолчанию Electricity (маркеры только у электрических нод, остальные не рисуются и не выбираются), вкладка Logic показывает ровно Number+Boolean, провода другого слоя скрыты,

  разрывает, перетаскивание от чужой ноды всё равно идёт от якоря, отпускание Ctrl забывает якорь; Ctrl, зажатый ДО выбора: первая нода становится якорем; клик по пустому месту снимает выбор; **Esc** — сначала отмена перетаскивания, затем снятие выбора (инструмент остаётся); **ПКМ** убирает все провода ноды; нарисованные

  непрозрачно, у блока с моделью без настроек — только полупрозрачна; наведение меняет фиолетовый на голубой и обратно; клик по блоку без настроек ничего не открывает; клик по мотору открывает панель СЛЕВА по схеме (порядок
  параметров, умолчания, клики по панели не проходят в мир); ввод значения меняет блок, вне границ — зажимается и показывается зажатое, мусор не меняет; Ctrl+Z откатывает по шагам; виджеты по типу (Enum — список, Float — поле); панель
  сиденья (8 параметров), режим и чувствительность пишутся именно этому сиденью; печать в поле панели не включает горячие клавиши `N`/`X`; **Esc** и клик по пустому месту закрывают панель, смена инструмента убирает все подсветки;
  провода и параметры, сделанные инструментами, переживают сохранение/загрузку.
- *`RunRealBlocksTests` (НАСТОЯЩИЙ `blocks/`):* для КАЖДОГО функционального блока каталога — ноды и ячейки портов внутри footprint'а (поймало `lf_out`/`ud_out` в клетке z=3 у сиденья), заявленное поведение реализовано (опечатка в `behavior`
  оставила бы блок мёртвым), id нод уникальны; контракты `pilot_seat` (четыре Number-выхода осей, `hotkey_1..6`, `occuped`, `triger_1/2` — все выходы; схема осей reset/sticky + sensitivity), мотора (Number- и Electricity-вход, Torque-выход,
  `maxPower`/`maxRpm`), аккумулятора, кнопки (`behavior: Button`, Boolean-выход), вала; **сквозная машина из настоящих блоков:** аккумулятор → мотор, сиденье (`ws_out`) → сигнал мотора, кнопка на питании, два вала над портом мотора: W

- *Числа мотора (в `RunRealBlocksTests`, настоящий мотор):* на сигнале 1 — ровно 3600 об/мин (60 об/с), расход 0.1 ед./с (1.0 за 10 с).
- *`RunNetworkedVehicleTests` (часть hosted-теста, один процесс; настоящий `NetHub`-сервер, чужие игроки — фиктивные peer id):* сервер создаёт тело на общем корне `NetVehicles` и ведёт его физику и рантайм (ждёт `PhysicsFrames`), собственный пол держит тело; копия-наблюдатель из того же JSON (одинаковые блоки/провода/параметры/`InstanceId`), заморожена, рантайм-зеркало не считает; пакеты поз (id, позиция, поворот, скорость) обновляют только адресата, копия догоняет позицию и поворот; правила сервера: сиденье занимает один игрок, нельзя сесть не на сиденье/на неизвестное тело, ввод принимается только от сидящего, встать может только сидящий; кнопка: чужой её не отпустит; снимок рантайма переносит занятость, ось, обороты, заряд и нажатую кнопку; отключение игрока освобождает сиденье, отпускает кнопку и сбрасывает ввод; хост садится/встаёт через `GameWorld` (сиденье занимает сервер); возврат тела убирает его, чистит учёт сидений и шлёт событие; регистрация копии клиентом без дублей; скрытие тел, пока пир в редакторе.

Хост ждёт клиента и спавнит тело; клиент получает копию, сверяет блоки/провода/параметры, садится (ответ сервера), держит W (обороты приходят снимками), жмёт и отпускает кнопку, встаёт, ждёт возврата тела. Оба процесса выходят с кодом 0 при успехе. Прогнан: оба варианта хоста — без ошибок.
- *`RunBlockEditorSchemaTests`:* редактор блоков сохраняет схему `Parameters` при пересохранении (с экранированием `<`/`&` в подсказках), игра читает её обратно; битая схема блокирует Save; пустое поле — компонент не пишется.

**Анимация довода призрака на J/K/L** (`BuildEditor._ghostVisualBasis`/`_ghostRotationFrom`/`_ghostRotationTo`, см.

**Редактор блоков** (`Dev.BlockEditor`, `--blockeditor`, `RunBlockEditorTests`, см. [05](05-world-and-vehicle-systems.md) «Редактор блоков») — добавляется как временный
ребёнок уже загруженного `editor`, блоки пишет во временную `user://selftest_blockeditor` (`BlockEditor.BlocksDirectory`), модель — самодельный `.gltf`
2×2×2 с началом координат в центре. UI глазами не проверить без живого дисплея, поэтому тест целится в то, что можно проверить:
- *Размещение модели:* Browse файла внутри проекта (путь `res://`, модель видна сразу, без импорта), рамка bbox — bbox.min в (0,0,0), 2 м при 0.125 = ровно клетка,
  footprint считается сам; масштаб по осям → footprint 3×1×2; допуск 1% (0.5% — не следующая клетка, 2% — следующая).
- *Якорь:* `SelectAnchor` пишет якорь в панель, Max по X у модели в 2 клетки сдвигает её в клетки −1..0 (`footprintMin = -1`), Center у модели в 3 клетки → −1..1;
  Ctrl+Z/Ctrl+Y откатывают/повторяют выбор якоря.
- *Выбор по экранным координатам* (через настоящую камеру, `Camera3D.UnprojectPosition`; клик в 3D-виде вызывает те же методы): `PickAnchor` по проекции угла bbox и центра грани
  даёт нужные доли, далеко от маркеров — `null`; `PickGizmoAxis` — по клику на каждой из трёх стрелок свою ось, мимо — `-1`.
- *Гизмо масштаба:* перетаскивание стрелки X на её длину удваивает масштаб ТОЛЬКО по X (и bbox/footprint следуют вживую), с Shift — по всем осям; весь жест — одна точка
  Undo; `ClosestParamOnAxis` (точка на оси, ближайшая к лучу; параллельный луч → 0) и `DraggedScale` (нижняя граница 0.001, остальные оси не трогает).
- *Коллизия клетками:* «+ Cells» (1×1×1 в (0,0,0)), «Fill footprint» (группа == footprint), Remove; группа может лежать вне footprint'а.
- *XML и круг запись→чтение:* текст XML содержит `scale`/`anchor`/автоматические `footprint`+`footprintMin` и клетки коллизии как целые индексы (без `size`, без
  legacy-ключей); Save → **каталог игры загружает сохранённый блок** тем же кодом (scene/scale/anchor, footprint == посчитанному редактором, 3 клетки → 2 бокса, behavior/
  capacity/params, имя/масса); сброс полей → `LoadSlug` → то же самое (клетки показываются слитыми боксами), порты (в т.ч. два в одной точке и ячейка с
  ОТРИЦАТЕЛЬНЫМ индексом), ноды (включая отрицательную клетку), params — без потерь.
- *Отказ сохранять:* конфликт нод, params не-объект, миллион клеток коллизии, модель, которая не загрузилась (footprint не посчитать) — файл на диске не тронут;
  блок без модели сохраняется как 1×1×1 плейсхолдер без `scene` и без коллизии; блок старого формата не грузится в игру и редактор пишет причину в статус, не падая.
- *Undo/Redo:* AddPort/Add collision group/Remove node откатываются (и поля, которых действие не касалось, возвращаются как были); `LoadSlug` начинает историю заново.
- *Browse вне проекта:* файл копируется в `res://meshes/` и сразу виден (4×2×2 ед. → 2×1×1 клетки).
- *Переэкспорт:* `PollModelFile` замечает изменённый файл (другой размер) и обновляет bbox/footprint (8×2×2 ед. → 4×1×1), на неизменённом — нет.

**Коллизия функциональных блоков в мире** (`World.VehicleSpawner`, `RunVehicleSpawnerCollisionTests`) — блок-фикстура с клетками коллизии `[-1,0,0] [0,0,0] [0,2,0]` и
`footprintMin = (-1,0,0)`. Чисто: для **всех 64 поворотов** клетки мира, покрытые боксами коллизии (через `InstanceFrame`), == корень + повёрнутые клетки блока. Через настоящий спавн:
1 автоматический бокс обычного `block` + РОВНО слитые боксы функционального (2) + 0 у функционального блока без коллизии; бокс 2×1×1 лежит над клетками 4 и 5
(рамка блока начинается с угла корневой клетки), оторвавшаяся клетка (0,2,0) — отдельный бокс над корнем вне footprint'а.

**Логические ноды, поведения и рантайм функциональных блоков** (`RunNodeAndBehaviorTests`, чистая логика без
сцены; см. [05](05-world-and-vehicle-systems.md) «Логика и рантайм функциональных блоков»):
- *Данные нод:* `"nodes"` разбираются в `Nodes` и НЕ попадают в физические `Ports`; id/type/direction/клетка `[x,y,z]`,
  регистронезависимые enum, умолчание клетки (0,0,0); неизвестный `type` (в т.ч. `Fluid`) — ошибка; позиция не из трёх
  чисел (2D-позиция порта) — ошибка; `"params"` (строка как есть, число как JSON-текст, fallback).
- *Правило размещения:* две ноды одного типа в одной клетке — ошибка загрузки, даже вход+выход; тот же тип в РАЗНЫХ
  клетках и РАЗНЫЕ типы в одной клетке — допустимы; `FindNodeConflict` называет обе ноды и возвращает null для корректной схемы.
- *Электричество — не физический ресурс:* старая запись порта `"resource": "Electricity"` падает с сообщением, указывающим
  на `"nodes"`.
- *Кнопка-фикстура* (`fx_button` из `BuildFixtureCatalog`): `FunctionalBlock` без `BuildingBlock`, behavior `"Button"` есть в реестре, `mode` ∈ {momentary,
  toggle}, `glowNode`/`glowColor` заданы и читаются, физических портов нет, а нод две — Electricity In (питание) и Boolean Out (состояние) в одной клетке
  (разные типы — легально); есть явная коллизия (клетка `[[0,0,0]]`).
- *`ButtonSettings`:* умолчания (momentary, `"Cap"`, `#33ff55`), явные значения (mode регистронезависим), пустой
  `glowNode`/нечитаемый `glowColor` → умолчания.
- *`ButtonBehavior`* на синтетических определениях: toggle (повторный Press без Release игнорируется, Release
  состояние не меняет, второй Press выключает), momentary (включён, пока держат; лишний Release ничего не меняет),
  умолчание и неизвестный `mode` → momentary, кнопка без выходной ноды молчит, чужая нода читается как «нет значения»,
  ключи без реализации не в реестре.
- *`FunctionalBlockRuntime`:* состояние только у блоков с поведением (не у обычных и не у блока с нереализованным поведением; на фикстурном каталоге), по
  экземпляру; вторая кнопка не сбрасывает первую; Release по режиму реальной кнопки; Remove выбрасывает состояние,
  новая кнопка на той же клетке — новый экземпляр с чистым состоянием; после `Dispose` рантайм постройку не слушает.
- *Спавн* (`RunFunctionalRuntimeSpawnTest`, кнопка-фикстура подставляется в каталог): у заспавненного `VehicleBody` есть `Runtime` с состоянием ровно у блоков с реализованным
  поведением, ключ состояния — `InstanceId`; нажатие поднимает выходную ноду кнопки; коллизия = 1 автоматический бокс обычного блока + ровно слитые боксы функционального.
- *Редактор блоков и ноды:* «+ Add node» ×3 даёт три РАЗНЫХ типа в одной клетке (сам конфликт не создаёт); три ноды (одна — в отрицательной клетке) и params
  (`mode`, `glowNode`, `glowColor`) переживают save+reload без потерь; конфликт нод (два Boolean в одной клетке, In vs Out) и params не-объект → Save отказывается, файл
  на диске не тронут; Remove node + Ctrl+Z. Геометрия: `ComputeNodeAnchor` — центр клетки, в т.ч. отрицательной, клэмп вне footprint'а.

- *Питание-заглушка и дебаг:* свежая кнопка обесточена; `DebugForcePowered` + `Tick` запитывает все блоки с состоянием, выключение
  обесточивает; питание не меняет сигнал; `InteractAll<ButtonBehavior>` нажимает/отпускает все кнопки; toggle: после
  Press+Release `Toggled` держится при `!Pressed` (`Active` следует за `Toggled`).

**Визуал кнопки** (`RunButtonVisualTests`, `Editor.ButtonVisual`, БЕЗ ассетов) — модель собирается в тесте кодом: корень +
`MeshInstance3D "Cap"` с общим `StandardMaterial3D` + `AnimationPlayer` с клипом, двигающим крышку вниз за 0.2 с (реальный
`Seek` в живом дереве сцены). Проверено: `pressProgress` идёт к 1 с конечной скоростью (не прыжок) и возвращается к 0, а крышка
на каждом шаге стоит в нужной доле хода; прерванное нажатие разворачивается с текущего места (0.4 → 0.2); обесточенная —
свечение остаётся 0 при полном нажатии; запитанная — свечение растёт каждый шаг и не обгоняет прогресс, выходит на
`MaxEmissionEnergy`; питание пропало посреди нажатия — свечение гаснет плавно (не обнуляется скачком), нажатие остаётся;
материал крышки — личная копия (общий оригинал не тронут), два экземпляра с ОБЩИМ материалом светятся независимо; выбор
клипа ("press" приоритетнее, иначе первый не-RESET); нет `AnimationPlayer`/узла `glowNode` — без ошибок, каналы независимы.

**Мультиплеер** (`Core.NetHub`/`NetEditOp`/`Core.UndoHistory`, см. [05](05-world-and-vehicle-systems.md)) — НЕ
сквозной тест двух игроков (нужны два реальных процесса игры, харнесс живёт в одном), а несколько независимых
проверок. Логика правок: `NetEditOps.Apply` (тот же код, что применяет и сервер перед рассылкой, и каждый клиент,
получив её) — все 6 видов правки, включая полную покраску по грани/региону формы (паритет с одиночным
редактированием, 2026-09-29 (6), не только целиком блок/клетка): `Place` ставит первый блок на пустую решётку и
блок, касающийся уже стоящего, но отказывает блоку, который ничего не касается (то же правило соседства, что и в
одиночном редактировании, `Core.PlacementRules`) и неизвестному слагу; `PaintFace` красит ровно одну грань решётки,
не трогая противоположную; `PaintRegion` красит наклонную/треугольную грань формы (Wedge, регион-рампа); `PaintInstance`

раньше — `PeekUndoAuthor` всегда `null`, Undo/Redo безусловны. Транспорт: настоящее ENet-рукопожатие сервер+клиент

**Геометрия форм** (`ShapeMeshBuilder`/`BlockGeometry`): для Wedge/Pyramid/InvertedPyramid — все треугольники имеют
верный обход вершин (нормаль совпадает с ожидаемой), все вершины остаются в границах 1×1×1; число треугольников
соответствует форме за вычетом граней с флагом `FullCoverage` (см. ниже) — их строит не `ShapeMeshBuilder`, а
`ChunkMesher`: Pyramid — 4 (без изменений, у него таких граней нет), Wedge — 4 (было 8 — низ и задняя стенка ушли в
`ChunkMesher`), InvertedPyramid — 4 (было 10 — `x=0`/`y=0`/`z=0` ушли в `ChunkMesher`); для Cube строитель возвращает
null (эту форму по-прежнему рисует `ChunkMesher`); Resize «двигает вершины» — bounding box меша масштабируется вместе
с размером экземпляра; вращение на 4 четверти вокруг одной оси возвращает исходную ориентацию, на 90° — заметно
меняет нормали; отражение по оси заметно двигает вершины (не просто сдвиг) и не ломает обход треугольников (винд
остаётся верным); для пяти поворотов асимметрично растянутого (3×1×1) скоса bounding box точно совпадает с ожидаемым
`Size×CellSize` (регрессия на баг, из-за которого повёрнутый растянутый блок визуально "плавал" не по границе клеток
— см. [03](03-build-editor.md)).

**Склейка/отсечение граней форм в `ChunkMesher`** (`ShapeMeshBuilder.FullCoverageMask`, `VoxelChunk.FaceMask`):
одинокая не-кубическая клетка добавляет в `ChunkMesher` только те грани, что покрывает ЦЕЛИКОМ (2 для Wedge — низ +
задняя стенка, 0 для Pyramid), остальное по-прежнему рисует её собственный меш; грань соседнего куба, обращённая к
клетке, которая эту сторону целиком НЕ покрывает, **остаётся видимой** (культить в этом случае значило бы оставить
дыру в стыке — было багом, исправлено); два соседних куба, а также кубы и формы, ЧЬИ ОБЕ обращённые друг к другу
стороны целиком покрыты и совпадают по цвету, по-прежнему/теперь нормально культят/склеивают общую грань (в т.ч.
между двумя формами, а не только кубами); две формы, повёрнутые так, что их полные грани обращены друг к другу,
взаимно культят этот стык (внутренняя, снаружи невидимая геометрия не рисуется).

**Resize многоклеточных форм** (`Construction.BoundaryFaceMask`, `ShapeMeshBuilder.ComputeOcclusionMask` — оба
найдены как баги на реальной постройке пользователя, см. WORKLOG): растянутый Wedge (5 клеток вдоль его закрытой
оси Z-) даёт РОВНО 1 склеенный полигон на низ и 1 на заднюю стенку, без единой лишней стены на внутренних границах
клеток (до фикса было 6 полигонов вместо 2 — по лишней стенке на каждой внутренней границе); то же самое проверено
и через `PlaceBlock` (за один вызов), и через `TrySetSize` (рост уже стоящего блока — маска у СТАРЫХ клеток тоже
пересчитывается, не только у новых); прямое воспроизведение бага пользователя — 3×2×8 InvertedPyramid даёт РОВНО
3 полигона (по одному на каждую из 3 полных сторон), и явная проверка данных: бит стороны стоит только у клетки на
истинной границе экземпляра, ни у одной внутренней. Отдельно — `ComputeOcclusionMask`: частичная (боковая) грань
формы не рисуется, когда её целиком закрывает полностью закрывающий сосед (проверено количеством треугольников до/
после), но остаётся видимой, если сосед не закрывает свою сторону целиком (другая форма её частичным бортом) или
закрывает только часть растянутой границы — оба сценария намеренно не дают дыр.

**Постройка, Resize, вращение и отражение** (`Construction`): `Place` создаёт экземпляр и владение клеткой, отказывает
на занятой клетке, принимает и хранит `RotationSteps`/`Mirror` (по умолчанию — без поворота/отражения); `TrySetSize`
растёт только от `Origin` в положительную сторону (сам `Origin` никогда не двигается), атомарно отказывает при занятой
клетке в новой области (размер не меняется вообще), зажимает запрошенный размер в `[1 .. MaxSize]` из `BuildingBlock`,
отказывает для блока без этого компонента; `Paint`/`Remove` действуют на все клетки многоклеточного экземпляра разом;
`PlaceBlock` (используется загрузкой и установкой блока игроком) ставит блок произвольного размера/поворота/отражения
одним вызовом.

**Вращение перед установкой** (`EditorState`): `RotatePendingX/Y/Z` независимо крутят X/Y/Z по модулю 4, 4 поворота
подряд по одной оси возвращают исходную ориентацию.

**Сохранение/загрузка** (`ConstructionIO`): сериализация → десериализация сохраняет слаг/позицию/размер/цвет/поворот/
отражение каждого блока; неизвестный слаг блока при загрузке пропускается, а не валит загрузку; round-trip через
настоящий файл (`user://`) — тот же код, что раньше стоял за кнопками Save/Load в редакторе.

**Именованные сохранения** (`ConstructionStorage`, см. [05](05-world-and-vehicle-systems.md)): `SanitizeFileName`
(небезопасные символы вырезаются, пустой результат — заглушка); каталог создаётся автоматически при обращении; первое
сохранение — `createdUtc == modifiedUtc` (один вызов времени на весь `Save`, не два независимых — иначе они почти
никогда не совпадали бы даже при первом сохранении); пересохранение по тому же пути сохраняет `createdUtc`, но
обновляет `modifiedUtc`/описание; `List()` находит сохранение по имени/пути; `ResolveNewPath` не даёт двум постройкам
с одинаковым названием перезаписать друг друга (`(2)`, `(3)` и т.д.). Реальный файл пишется и удаляется в НАСТОЯЩЕЙ
папке "Документы" ОС (не `user://`) — узнаваемым именем (`__selftest_storage__`), с очисткой в `finally` независимо
от результата проверок. Рендер превью (PNG) в эти тесты сознательно не входит — требует нескольких реально
отрисованных кадров, ненадёжно в headless-окружении текущей среды разработки (см. class doc
`Editor.ConstructionPreviewRenderer`); проверено только вручную, на обычном запуске игры.

**Диалог сохранения** (`Ui.SaveDialogUi`, через реальный ввод): клик по Save открывает диалог; горячие клавиши
редактора (проверено на "1" — слот хотбара) не срабатывают, пока диалог открыт — иначе печатать название было бы
невозможно; Esc закрывает без сохранения, как и Cancel; Done с пустым именем не закрывает диалог (имя обязательно);
Done с именем/описанием закрывает диалог и создаёт файл с этими метаданными, что подтверждается через
`ConstructionStorage.List()`.

**Не покрыто самотестами** (см. [05](05-world-and-vehicle-systems.md) за подробностями): верстак
(`World.Workbench`/`WorkbenchMenuUi`), кнопки Exit/Spawn и `World.VehicleSpawner` — весь путь верстак→редактор→
Spawn/Exit→мир требует реальной смены главной сцены (`SceneTree.ChangeSceneToFile`), а самотесты сейчас устроены
так, что живут ВНУТРИ одной уже загруженной сцены (`BuildEditor`, см. `SelfTest.RunPlayerAndWorldTests` ниже —
инстанцирует `GameWorld` как обычного ребёнка именно чтобы не тянуть смену сцены в тест); как ЭТО выглядит в игре
(модель верстака, расположение) проверено только вручную.

**Редактор через имитацию реального ввода** (`Input.ParseInputEvent`, полный путь события через GUI и `_Input`/`_UnhandledInput`):
редактор при входе сам ставит корневой блок 1×1×1 в центральную клетку (0,0,0) (`BuildEditor.PlaceRootBlock`) —
проверено ДО того, как остальные тесты расчищают сцену под себя (`Construction.Clear()`, не голый `grid.Clear()`,
иначе `Construction` продолжала бы считать эту клетку занятой своим экземпляром). Призрак блока над клеткой
размещения непрозрачен (`Transparency == Disabled`, альфа = 1 — выглядит как уже установленный блок, не
полупрозрачная подсказка) и включает FullCoverage-стороны формы (`includeFullCoverageFaces`, см.
[03](03-build-editor.md)) — проверено прямым подсчётом треугольников меша призрака Wedge (8, не 4); ЛКМ на
землю/грань блока (установка), ПКМ без инструмента ничего не делает. **Соседство** (`CanPlaceFootprint`/
`TouchesExistingBlock`): клетка, касающаяся уже стоящей постройки только по диагонали (через ребро/угол, 0 общих
граней) не принимает блок — ни призрак, ни клик — а клетка встык (по грани) по-прежнему работает как раньше; сама
установка на пустую площадку (нет ни одного блока вообще) не блокируется — иначе самый первый блок в постройке
поставить было бы некуда. Paint и Delete — оба на ЛКМ
(`BuildEditor.ButtonFor`, не конфликтуют — взаимоисключающие режимы; ПКМ инструментам не назначена вообще):
проверено, что, пока активен любой из них, призрак скрыт и ЛКМ не ставит блок (а выполняет инструмент), что ПКМ не
действует ни для Paint, ни для Delete, и что призрак снова появляется после деактивации инструмента. Paint красит
РОВНО ту грань клетки, в которую попал луч (`VoxelGrid.GetFaceColor`, не `GetColor` — представительная грань X-
других 5 граней той же клетки остаётся нетронутой), если клетка закрывает эту грань целиком (`FullCoverage`) — а
если нет (наведение на сторону формы, которую она не покрывает целиком, например «верх» Wedge — проверено прямым
наведением камеры сверху вниз и сверкой `RayHit.Normal`), красится РОВНО та грань формы (`BlockInstance.RegionColors`,
`Construction.PaintRegion`), которой принадлежит попадание, а не весь экземпляр целиком — проверено и для «своей»
осеориентированной грани (левый треугольный борт Wedge, наведение камеры вдоль +X на грань X-, попадает напрямую по
индексу), и для отката на диагональную грань (рампа Wedge при попадании в Y+, у которой своей грани нет), и что оба
точечных цвета сосуществуют, не перезаписывая друг друга и не трогая представительный `Color` экземпляра. Отдельно
(без сцены, чистая логика) — `ShapeMeshBuilder.TryRaycastFace` (настоящее пересечение луча с реальной геометрией
формы, не приближение по стороне ограничивающего куба): луч, направленный точно в центр диагонального среза
InvertedPyramid, попадает в него напрямую (индекс грани 6) — раньше это было принципиально недостижимо, — луч, не
направленный на форму вообще, ничего не пересекает (не даёт ложных срабатываний позади источника луча), и что для
уже работавшего случая (левый борт Wedge) точный рейкаст даёт тот же результат, что и приближение по направлению;
`ShapeMeshBuilder.TryFindPaintRegion` (запасной вариант) — для всех значимых осевых направлений всех трёх форм
(Wedge/Pyramid/InvertedPyramid), включая отказ для Cube, и что `BuildData` с `regionColors` красит только указанную
по индексу грань, остальные — в общий цвет, как раньше. Независимые переключатели
Wireframe/Borders (solid/wire/border видимость по всем 4 комбинациям, не общий цикл), клавиша 3 выбирает слот хотбара
(колесо мыши больше не листает хотбар — крутит `FlyCamera.Zoom`, проверено в обе стороны: камера двигается вдоль
направления взгляда, слот хотбара не меняется), Tab/Esc, блокировка кликов по миру при открытом списке блоков и над
UI, клики по слотам хотбара, кнопкам
тулбара и карточкам блоков (всегда ЛКМ — см. [03](03-build-editor.md) про UI-конвенцию); индикатор активности на
кнопках-переключателях тулбара появляется/исчезает вместе с инструментом; разворачивание/сворачивание палитры Paint
вместе с инструментом; 3 RGB-ползунка меняют цвет покраски вживую; «+ Save color» добавляет новый свотч в личную
палитру.

Панель Resize на тулбаре — независимый переключатель (кнопка не трогает `state.Tool`), поля всегда активны и
редактируют `EditorState.PendingSize` напрямую, без ПКМ/цели: кнопки «+»/«−» и прямой ввод в текстовое поле меняют
`PendingSize` (0/пустое/нечисло откатывается на предыдущее значение, «-» отфильтровывается при вводе); ЛКМ ставит
блок сразу такого размера — дальнейшие правки `PendingSize` уже поставленный блок не меняют (это и было целью
переделки — раньше Resize растягивал блок под курсором). Клавиши J/K/L вращают следующий размещаемый блок вокруг
X/Y/Z, клавиши U/I/O отражают его по X/Y/Z (`EditorState.PendingMirror`, переключатель туда-обратно) — оба вида
проверены на том, что реальные нажатия клавиш меняют состояние ожидания, сохраняются в поставленном экземпляре, и,
главное, **не** трогают уже поставленный блок под курсором (включая явный тест-регрессию на баг прежней версии,
которая по этим же клавишам двигала наведённый блок на +1 клетку). Перетаскивание Paint и Delete (оба ЛКМ) с
зажатой кнопкой по ряду блоков, отсутствие «проедания» при неподвижной мыши.

`Ctrl+Z`/`Ctrl+Y` через реальные нажатия клавиш (с `CtrlPressed`): ЛКМ-размещение отменяется/повторяется; отмена
игнорируется, пока фокус на текстовом поле (в панели Resize) — так убедились, что она не перехватывает отмену
текста; перетаскивание Delete (ЛКМ) отменяется **одним** шагом `Ctrl+Z`, а не по клетке — блоки для
этого теста ставятся по-настоящему (ЛКМ), а не заливкой `DemoBuilds.Fill` в обход `Construction`, как соседние тесты
перетаскивания — иначе отменять нечего, `Construction` о них не знает (см. `UndoHistory` в [03](03-build-editor.md)).
`UndoHistory` отдельно покрыт логикой без сцены: пустая история на старте, действие без изменений (занятая клетка)
не создаёт запись, `Undo`/`Redo` меняют содержимое `Construction` (включая цвет экземпляра), новое действие после
`Undo` стирает ветку `Redo`, `Redo` на пустом стеке ничего не делает. Отдельно — точечная покраска ОДНОЙ ГРАНИ
клетки (`VoxelGrid.TryPaintFace`, без изменений в `Construction`/`ConstructionIO.Serialize`) и точечная покраска
ОДНОЙ ГРАНИ ФОРМЫ (`Construction.PaintRegion`, без изменений в представительном `Color`) — обе всё равно создают
запись в истории и корректно откатываются/повторяются `Undo`/`Redo` (снэпшот — не просто JSON, см.
`UndoHistory.Snapshot` class doc и [03](03-build-editor.md), «Покраска по грани»).

> В headless-режиме у окна нет размера (вьюпорт 64×64), поэтому тест сам задаёт корневому окну 1600×900 —
> иначе вёрстка UI и проекция курсора на мир бессмысленны. Захват мыши в headless не проверяется (только смена yaw камеры).

## Скриншот-харнесс (визуальная проверка)

Запуск в оконном режиме (не headless), результат — PNG вьюпорта (включая UI):

```powershell
<EDITOR> --path . --resolution 1600x900 -- --demo=house --screenshot=out.png --cam=7,4.5,9,0,1.0,0
```

| Аргумент | Действие |
|---|---|
| `--demo=house\|stress\|shapes` | построить демо (`house` — дом на 1622 блока, `stress` — плита 80 000 блоков, `shapes` — по одному Block/Wedge/Pyramid/InvertedPyramid в ряд, включая повёрнутый/растянутый/отражённый экземпляры и группу куб+скос впритык для визуальной регрессии на дыру в стыке — см. [03](03-build-editor.md)) и вывести время/число полигонов |
| `--cam=px,py,pz,tx,ty,tz` | позиция камеры и точка, на которую она смотрит (метры) |
| `--wireframe=0\|1` | инструмент Wireframe (только полигоны+диагонали, без сплошных граней) |
| `--borders=0\|1` | инструмент Borders (чёрные границы отдельных клеток/блоков; включён по умолчанию) |
| `--tool=paint\|delete` | активировать инструмент Paint или Delete (оба на ЛКМ, см. [03](03-build-editor.md)) |
| `--resize` | открыть панель Resize на тулбаре |
| `--slot=N` | выбрать слот хотбара (0-based; по умолчанию 0 = "block") |
| `--size=x,y,z` | задать размер следующего ставящегося блока (`EditorState.PendingSize`) |
| `--mirror=x,y,z` | отразить следующий ставящийся блок по отмеченным осям (ненулевой компонент переключает ось) |
| `--picker` | открыть список блоков |
| `--hover=x,y` | навести курсор в пиксель (для «призрака» и контура цели) |
| `--frames=N` | сколько кадров ждать до снимка (по умолчанию 10; 300 — чтобы FPS в инфо-строке успел стабилизироваться) |
| `--screenshot=путь.png` | сохранить снимок и выйти |

## Замеры (встроенная Intel UHD Graphics, 1600×900)

- Демо-дом: 1622 блока → меш собран за 78 мс; 217 полигонов вместо 3196 граней.
- Плита 80 000 блоков: построение + меширование 314 мс; 160 полигонов вместо 23 200 граней.
- FPS ≈ 30 с тенями и MSAA (упирается в видеокарту и вертикальную синхронизацию; геометрии мало).
